# 附件全量审计

> 审计对象：`系统板块汇总(1).zip` 解压所得材料。  
> 审计口径：`[明示]` 表示 Markdown 直接写明，`[截图]` 表示视觉证据，`[资产]` 表示编译产物或网页文件中的证据，`[推断]` 仅表示可供后续需求访谈验证的合理角色/语义，不等同于已经确认的需求。  
> 隐私与安全：本报告不复述附件中的明文凭据、内网地址、个人姓名、头像或内部账号值，只记录其存在、用途类型和风险。

## 1. 覆盖范围与结论

| 材料 | 数量 | 审阅状态 | 主要用途 |
|---|---:|---|---|
| Markdown | 1 | 全文逐段阅读 | 当前页面、模块、字段、算法说明与运维说明 |
| PNG 截图 | 109 | 109/109 逐张视觉检查 | 现有 UI、数据密度、交互线索与空状态 |
| CSV | 2 | 全列、类型、缺失、枚举、时间与样例检查 | OMS 委托及持仓数据结构 |
| 原始嵌套网页资源压缩包 | 1 | 清点，不改动 | AI 景气度页面的原始保存资源 |
| 解出的网页资源 | 32 | 全量清点并检查关键源码/样式 | 前端栈、路由、API 形态和 AI 仪表盘结构 |
| 源文件合计 | 145 | 全量入册 | 见 `attachment_inventory.csv` |

核心发现：

1. 附件不是一份完整需求规格，而是“现有页面清单 + 局部字段说明 + 截图 + 两个导出样例 + 部分编译产物”的离散材料。它足以恢复业务版图与大量页面字段，但不足以直接确定平台边界、权限、SLA、数据治理和交易安全要求。
2. 当前业务版图至少覆盖六大域：工作台、数据资讯、交易风控、量化投研、主动投研、产品/经营报表；编译资产还暴露了学习中心、私有云、系统管理、市场运营等未在周报中完整展开的域。
3. 现有 UI 实际并存四套视觉语言：黑底行情终端、深色 OMS/IMS 监控、浅色企业数据工作台、独立的 AI 景气度响应式仪表盘。它们尚未形成统一设计系统。
4. 附件中含有高风险敏感信息：明文口令、内部网络端点、账户配置、运维路径与命令、可识别头像/姓名。设计阶段应立即做凭据轮换、材料净化、密钥托管和日志审计。
5. 两个 CSV 证明 OMS 业务已经有较清晰的订单/持仓数据结构，但存在枚举未释义、毫秒时间戳、超出 JavaScript 安全整数的 ID、展示单位混入字段名、全空目标字段等建模问题。
6. 嵌套资源证明现平台主前端为 Umi/React 企业应用，并混用 Ant Design、DevExtreme、ECharts、Chart.js；同时存在 DVA 状态模型、按路由拆包、WebSocket、DataHub/SQL 类 API、统一认证/路由服务和微前端插件痕迹。

## 4. 两个 CSV 的结构与语义

### 4.1 OMS 委托导出

- 文件规模：2,474 行数据、20 列；UTF-8，可由 `utf-8-sig` 稳定读取；无整行重复。
- 业务粒度：一行一笔 OMS 委托/订单事件快照。
- 证券范围：731 个不同证券代码；同一证券可有多笔委托。

| 类型 | 列 |
|---|---|
| 标的 | 证券代码、证券名称 |
| 方向/枚举 | 方向、状态、委托类型、开平、买卖 |
| 数量与价格 | 委托数量、委托价格(元)、成交数量、成交均价(元) |
| 时间 | 委托时间、已报时间、更新时间、交易日 |
| 标识 | 本地委托号、委托序号、内部委托信息 |
| 上下文 | 备注、操作员 |

类型与质量：

- `证券代码/名称`、方向、备注、操作员、委托序号应为字符串。
- 数量、状态码、委托类型、开平、买卖为整数；价格为十进制定点数，不应在核心账务中用二进制浮点。
- 四个时间字段均是毫秒 Unix 时间戳；样本覆盖同一交易日约两小时的委托窗口。UI/接口必须显式规定时区。
- `本地委托号` 约 19 位，超过 JavaScript `Number.MAX_SAFE_INTEGER`，必须全链路按字符串/UUID 处理。
- 状态实际出现 6 个代码值，但附件没有代码表；委托类型、开平在样本中均为单一值，不能据此假定生产上只有一种。
- 备注约 99.8% 为空；非空记录体现拒单原因。应拆分为结构化错误码、错误来源、可读消息，而非只留自由文本。
- “方向”与“买卖”疑似同义的文本/数值双编码，应确定规范字段与兼容映射。

### 4.2 OMS 持仓导出

- 文件规模：802 行数据、30 列；UTF-8；无整行重复。
- 业务粒度：同一账户、同一交易日下，一行一证券的持仓/损益快照。
- 证券范围：802 个不同证券代码，样本内一证券一行。

| 类型 | 列 |
|---|---|
| 标的/账户 | 证券代码、证券名称、账户、多空、结算 |
| 市场表现 | 涨跌幅%、现价(元)、昨盯市价(元)、昨收价(元) |
| 损益 | 盈亏(万)、平仓盈亏(万)、持仓盈亏(万)、昨仓盈亏(万)、T0盈亏(万)、日初持仓盈亏(万) |
| 市值与仓位 | 市值变动(万)、持仓市值(万)、持仓比例% |
| 持仓数量 | 当前持仓、昨收持仓、可用持仓、目标偏差量、目标持仓、今日买入、卖冻结 |
| 交易金额 | 买入(万)、卖出(万) |
| 时间 | 更新时间、创建时间、交易日 |

类型与质量：

- 标的和账户为字符串；数量为整数；比例、价格、目标字段为十进制定点数；时间为毫秒时间戳。
- `目标偏差量`、`目标持仓` 在 802 行中全部为空，说明导出模式未计算、字段未接入或业务上不适用，需要显式状态而不是静默空值。
- 多个损益/昨仓/T0/结算字段在样本中恒为 0，不能据此删列，但应核查仿真环境是否真的提供这些语义。
- 38 行创建时间为 0；0 不应与合法时间混用，应改为 `null + missing_reason`。
- 金额直接以“万”写入列名，适合展示但不适合作为规范存储。核心模型应保存原币种最小单位/定点金额，并把显示单位作为视图配置。
- 只有一个账户值且属于仿真环境，不能代表多账户、多币种、融资融券、港股/期货等生产情形。

### 4.3 CSV 建模建议所需的待确认项

1. 状态、委托类型、开平、买卖、多空、结算的完整代码表、版本和兼容策略。
2. 订单—成交—持仓—划拨的主键、幂等键、事件序列号和修订语义。
3. 金额/价格精度、币种、汇率、证券数量单位、市场与时区。
4. “快照”还是“事件流”；重放和事后修订如何表达。
5. 仿真、测试、生产数据隔离与脱敏级别。

### 6.2 编译资产反映的路由结构

bundle 中可恢复约 80 个命名路由。顶层结构至少包括：

1. 工作台：方案配置/编辑、只读用户方案、分享方案、小进 AI/搜索。
2. 数据资讯：实时资讯、数据集市/详情、数据字典、投资日历、基础数据、数据基础设施、AI 工具箱。
3. 交易风控：算法交易、RMS、Genesis 的 Algohub/OMS/IMS、分仓 UFT。
4. 投资研究：量化投研、主动投研、研究辅助、私有云。
5. 市场运营：产品/客户/结算/TRS 等报表。
6. 学习中心。
7. 系统与运维：机器人、应用服务、工作流、资源权限、数据预览，以及代码、镜像、调度、配置、跳板等外部运维入口。

编译 CSS 文件进一步对应财报详情/披露、重点股票、项目报告、市场估值、主题点亮、股票池、一平观点等主动投研页面。

### 6.3 API 与通信形态

- REST 风格 `/api/...`：统一认证、用户/角色/路由、DataHub 数据查询/推送、消息订阅、配置中心、ECS/私有云、风险和 What-if 等。
- WebSocket：存在 UFT 实时通道路径。
- 数据访问：前端代码中存在通用 SQL 查询/推送封装和字符串拼 SQL 的痕迹。后端必须强制参数化、资源级鉴权、查询白名单、行列级权限、审计和限流；不能只依赖前端过滤。
- 状态与事件：Markdown 配置表明 OMS 使用 Redis 发布订阅、数据/交易/同步事件总线、共享内存行情订阅和周期快照。
- 微前端/外链：部分研究辅助和运维页面是外链或 iframe，而非同一应用内的原生模块。

### 6.4 AI 景气度静态页的完整结构

`semi-tracker.html` 是独立保存的静态页面，不是 Umi 页面源码。它包含：

- 深蓝色固定左侧栏（桌面宽 155px）与浅灰内容区；
- 8 个主导航：核心检查清单、GPU 价格、金融市场监控、Token 用量、美国电力、上市公司指标、AI 巨头监控、研报观点；
- 额外的“北美数据中心监控”区块；
- 顶部检查清单、绿/黄/红阈值说明、整体警惕级别和可点击展开的指标解读；
- GPU 租赁/长租/AWS 现货、代际价差、占用率、预测市场、芯片销量；
- CDS、Token、推理价格、电力负荷、签约电力、折旧率、资本开支、ARR、估值和数据中心规模等图表；
- 内嵌 JSON 数据快照、Chart.js 图表初始化、滚动激活导航、窗口 resize；
- 响应式断点 1100/840/480px；移动端侧栏转顶部胶囊导航，图表改单列；
- 研报观点卡片及下载菜单。

重要限制：

- 页面是“生成时快照”，不是可证明实时更新的应用；数据新鲜度和生成时间只是一段静态文本。
- 数据 payload 内嵌在 HTML 中，体积约 1MB；生产设计不宜把大数据快照直接塞入首屏 HTML。
- 页面含保存来源的绝对内部链接，不具备直接移植性。
- `0` 是与业务页面无关的可识别人物照片，应从技术附件、构建产物和未来交付包中删除或做合法授权与访问控制。

## 7. 视觉与交互体系审计

| 视觉族 | 代表截图 | 优点 | 问题 |
|---|---|---|---|
| 黑底行情终端 | 0–2、8–12 | 信息密度高、贴近交易员习惯 | 小字号、红色网格过强、可访问性和响应式未知 |
| 深色 OMS/IMS | 20–23 | 实时状态、服务实例和明细同屏 | 极度拥挤、横向滚动、个人信息/环境信息暴露 |
| 浅色企业工作台 | 3–7、13–19、24–100、102–108 | 表格、筛选、报表模式统一 | 多个页面空白区域大；表头层级、单位和空状态不一致 |
| AI 景气度独立页 | 101 + HTML | 响应式、语义色、信息层级清楚 | 与主站组件体系脱节；静态数据与阈值解释耦合 |

共性交互模式：

- 筛选：日期/日期范围、证券、行业、账户、状态、来源、关键词、多选标签。
- 表格：排序、列搜索、分页、横向滚动、列分组、汇总、明细/汇总切换。
- 可视化：图表标签页、多序列选择、悬浮提示、时间缩放、热力图、空状态。
- 操作：刷新、新建、导入、上传、导出 Excel、查看详情、编辑/删除、收藏/外链。
- 导航：主域—子域—页面；部分页面为外链/iframe。

需要统一的设计令牌与规范：

1. 字体、数字等宽、最小字号、表格密度与宽表冻结列。
2. 金融语义色与通用风险语义色的冲突处理；不能只靠颜色表达。
3. 空值、零、未计算、无权限、数据延迟、加载失败的不同状态。
4. 元/万/亿、百分比、BP、毫秒/微秒、时区和小数精度的显示规范。
5. 搜索、筛选、刷新、导入/导出、危险操作和批量操作的统一反馈。
6. 生产/仿真/测试环境的强识别与不可误操作防护。

## 8. 明确约束、风险与未决问题

### 8.1 已见约束

- 期指基差 sigma 范围 0.5–3。
- 因子预测期 1/5/10；分组 2/3/5/10/20。
- 算法厂商能力、市场、集合竞价、涨跌停、市占率和异常处理各不相同。
- 算法单元有进度优先、资金/持仓不足跳过、错单阈值后暂停等自然语言规则。
- 系统区分生产、仿真、测试环境。
- OMS 有 API、Redis Pub/Sub、事件总线、共享内存行情和周期快照。
- UI 中存在大量宽表、实时刷新、历史分析与导出。

### 8.2 高优先级风险

1. **凭据泄露**：Markdown 含明文密码/秘密和内部地址；立即轮换并清理历史。
2. **个人信息**：截图头部和嵌套 JPEG 含可识别个人信息；材料需脱敏、最小化和授权。
3. **超大 ID 精度**：OMS 本地委托号不能进 JavaScript Number。
4. **SQL/数据权限**：编译资产含通用 SQL 查询与字符串拼接痕迹；需要服务端强鉴权和参数化。
5. **交易安全**：现有运维依赖命令行、强制杀进程、盘中手改配置；缺少审批、回滚、审计和高可用描述。
6. **枚举与单位不透明**：订单状态码、BP/VMAP 命名、多个无标题表头、以“万”为存储列名。
7. **快照与实时混淆**：AI 仪表盘是静态生成页，部分报表和图表大量空状态；必须显示数据时间、延迟和计算状态。

### 8.3 需求访谈必须补齐的问题

1. 平台目标、MVP 范围、各模块优先级和替换/复用现系统的边界是什么？
2. 用户、组织、基金、产品、策略、账户、资产单元之间的权限继承和数据隔离如何定义？
3. 哪些操作可写、可交易、可发布、可导出；谁审批、谁复核、谁审计？
4. 证券、指数、行业、产品、账户、订单和因子的规范标识及版本是什么？
5. 每个数据源的授权、频率、延迟、质量 SLA、血缘、修订和保留期是什么？
6. 订单/成交是事件流还是快照；如何幂等、纠错、回放、对账和追溯？
7. 交易与风控的延时、可用性、RTO/RPO、容量、灾备和降级目标是什么？
8. 因子回测的时间对齐、复权、幸存者偏差、未来函数、成本、样本外和可复现规则是什么？
9. 报表/推荐/评级的发布、复核、利益冲突、免责声明和历史版本如何管理？
10. 图数据库、向量数据库、消息队列、对象存储分别承载哪些对象和工作负载？谁是事实主源？
11. 数据集市和数据字典是否合并为同一数据产品目录？
12. “行业周期研究已停用”等旧模块应迁移、归档、只读还是删除？
13. 图片、视频、研报附件等非结构化内容的格式、大小、版权、转码、OCR、检索和生命周期是什么？
14. 主站、外链、iframe 和微前端的边界、单点登录、权限透传和审计如何统一？

## 9. 对后续总体设计的直接输入

本附件可以可靠地作为：

- 业务域与页面版图的初始清单；
- 订单、持仓、算法、因子、投研与报表对象的字段候选集；
- 现有视觉模式与交互模式的参考；
- 迁移盘点和差距分析的“现状基线”；
- 本体建模时的术语来源与关系假设。

但不能直接作为：

- 生产系统的完整需求规格；
- 后端架构、数据库选型或本体真源的唯一依据；
- 风控/算法规则的可执行规范；
- 权限、合规、SLA、灾备和验收标准。

后续设计应把这些离散页面重新组织为“对象—关系—动作—策略—证据—权限—事件—视图”的统一模型，而不是照截图逐页重做。
