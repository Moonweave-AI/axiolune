可观测性与 SRE

1. 运行目标

可观测性必须回答四类问题：

  1. 系统是否健康：请求、资源、队列、依赖和发布状态；
  2. 业务是否正确：订单/成交、风险、持仓、净值和对账不变量；
  3. 数据是否可信：新鲜度、完整性、顺序、血缘和点时状态；
  4. 谁在何种上下文做了什么：动作、授权、审批、版本和证据。

技术可用不代表业务可用。例如 HTTP 200 但行情滞后、持仓未核对或搜索索引少数据，都应计入相应服务等级。

2. 信号体系

2.1 统一上下文

OpenTelemetry Trace、Metric、Log 和业务事件共享：

  • trace_id、span_id、correlation_id；
  • action_id、workflow_id、event_id；
  • object_type/object_id（敏感 ID 可哈希或受控引用）；
  • service.name/version、ontology.version、policy.version；
  • environment、region/zone、deployment_id；
  • data_as_of、source、replay_id；
  • 经过最小化处理的组织、用途和分类。

日志不得记录令牌、完整请求体、密钥、受限字段或未脱敏文档内容。

2.2 四类遥测

信号 示例 推荐后端
Trace Object Query → Policy → Domain → DB；Action → Workflow → OMS OpenTelemetry + Tempo/等价
Metric RED、USE、Kafka/Flink、数据库、GPU、业务计数 Prometheus/VictoriaMetrics + Grafana
Log 结构化诊断、错误、适配器回执摘要 Loki/OpenSearch/等价
Audit/Event 授权、动作、发布、数据质量、业务事实 Kafka + ClickHouse/WORM

审计和业务事实不能依靠会采样、过期或被运维修改的普通日志保存。

3. 服务目录与依赖图

每个运行组件在服务目录登记：

  • 业务/技术 Owner、值班组、严重度和支持时间；
  • API、Topic、数据库、数据产品和外部依赖；
  • Tier、SLO、容量上限、RTO/RPO；
  • 仪表板、告警、运行手册、发布和恢复链接；
  • 数据分类、许可证、地域和成本中心；
  • 最新版本、变更窗口和退役状态。

服务目录与本体 SystemComponent、DataAsset、ExternalSystem、ActionType 建链接。故障影响分析不依靠过期的手工拓扑图。

4. SLI 与 SLO

4.1 定义规则

一个 SLI 必须明确：

  • 计量事件和采集点；
  • 成功/合格条件；
  • 统计窗口和排除项；
  • 环境、用户旅程或业务分区；
  • 数据完整性和迟到处理；
  • Owner 与决策用途。

可用性 SLI：

[ Availability = \frac{\text{合格请求或业务事件}}{\text{全部有效请求或业务事件}} ]

延迟 SLI 用分布/直方图计算 P50/P95/P99，不能用平均值替代。数据新鲜度：

[ FreshnessLag = t_{\text{now}}-\max(t_{\text{source event}}) ]

4.2 初始 SLO 目录

以下是工程基线，需在容量、监管和柜台约束确认后固化为合同：

用户旅程/能力 SLI 初始目标
风控硬限制判定 正确完成率与平台内 P99 ≥99.99%；时延由端到端预算反推
订单提交受理 非用户错误成功率、P99 ≥99.99%；P99≤500 ms（不含外部回执）
订单状态到监控 UI 来源回执至可见延迟 P95/P99 P95≤1 s；P99 阈值专项确认
常规对象详情 授权后成功率、P95 ≥99.95%；P95≤500 ms
权限感知搜索 结果完整率、P95 ≥99.9%；P95≤1.5 s
常用分析视图 成功率、P95 ≥99.9%；P95≤3 s
关键行情 消息完整率、序号缺口、端到端新鲜度 按市场/来源分开定义
持仓/资金 核对及时率、未解释差异 截止点 100% 核对；差异有时限
数据产品 准时率、质量通过率 按产品 SLA；关键资产单独目标
工作流/审批 受理可用性、积压时长 ≥99.95%；积压按风险告警
研究/报表 作业按期完成率 ≥99.9% 服务；业务截止按报告定义

4.3 错误预算

若 30 天 SLO 为 99.95%，理论不可用预算约 21.6 分钟。错误预算用于决策：

  • 预算健康：允许正常功能发布；
  • 消耗过快：降低发布并优先可靠性修复；
  • 预算耗尽：除安全/故障修复外冻结风险性变更；
  • Tier 0 交易事故即使未耗尽预算也可触发冻结。

告警使用多窗口、多燃烧率，示例：

  • 快速：1 小时窗口燃烧率 ≥14.4 且 5 分钟确认；
  • 慢速：6 小时窗口燃烧率 ≥6 且 30 分钟确认；
  • 趋势：3 天窗口用于计划，不呼叫值班。

具体阈值按 SLO 和流量校准，避免“每个错误都告警”和“只看月末平均”。

5. 指标目录

5.1 服务 RED 与资源 USE

  • Rate：请求/事件/任务量及业务分区；
  • Errors：稳定错误 code、拒绝、超时、部分失败；
  • Duration：端到端及每依赖延迟；
  • Utilization：CPU、内存、磁盘、网络、连接、线程、GPU；
  • Saturation：队列、连接池、消费者积压、GC、IO wait；
  • Errors：主机/容器、文件系统、网络和硬件错误。

5.2 数据与流

  • 来源/处理/发布时间和端到端 freshness；
  • Kafka offset lag、消费速率、分区偏斜、ISR；
  • Flink checkpoint 时长/失败、watermark、backpressure；
  • 数据行数、唯一性、null、范围、分布漂移、隔离量；
  • Schema/枚举未知、点时回填、血缘断裂；
  • Iceberg 小文件、快照、compaction 和 orphan；
  • 索引计数差、更新滞后和重建进度。

5.3 交易与风险

  • 行情入站/解析/发布/消费各段延迟，序号缺口和主备源；
  • 母单/子单各状态数量和停留时长；
  • 提交—柜台回执—交易所回报各段延迟；
  • UNKNOWN_EXTERNAL_STATE、重复回执、拒单、撤单和部分成交；
  • 风险规则耗时、拒绝率、例外、规则版本和超时；
  • 账户可用量、持仓、资金、成交和订单核对差异；
  • 网关心跳、会话、序号、重连和降级模式；
  • TWAP/VWAP/POV 等算法执行偏差及数据可用性。

5.4 本体、搜索与 AI

  • 对象解析命中、主键冲突、链接悬空和物化延迟；
  • 本体版本采用率、旧 SDK 调用和弃用依赖；
  • 策略判定延迟、允许/拒绝/错误和缓存失效；
  • 搜索/图/向量 ACL 过滤时延与索引差异；
  • 模型延迟、错误、漂移、成本、回退和人工接管；
  • Agent 检索无证据、引用不支持、工具拒绝、危险提案和预算；
  • 自动化重复触发、重试、补偿、人工队列和积压年龄。

6. 仪表板层次

  1. 高管/业务态势：关键市场、订单、风险、数据和客户旅程，不暴露实现噪声；
  2. SLO 总览：每服务错误预算、可用性、延迟和当前发布；
  3. 领域看板：行情、OMS/RMS、组合、数据产品、报告、Agent；
  4. 依赖看板：Kafka、PostgreSQL、ClickHouse、OpenSearch、对象存储、工作流；
  5. 发布看板：版本、金丝雀、差异、回滚门和变更事件；
  6. 事件调查：按 trace/action/order/account/data asset 深链到相关信号。

每张面板注明数据源、更新频率、时区、口径、Owner 和最后验证日期。

7. 告警设计

一个可呼叫告警必须具备：

  • 用户/业务影响或迫近的 SLO 风险；
  • 明确严重度、Owner 和响应时限；
  • 足够上下文：环境、版本、影响对象、最近变更、依赖；
  • 可执行运行手册；
  • 恢复条件和抑制/关联规则；
  • 定期检验并统计误报、漏报和无人处理。

应优先告警：

  • SLO 多窗口燃烧；
  • 交易/行情状态机不变量破坏；
  • 外部未知状态和核对差异；
  • 数据新鲜度/完整性越过业务截止；
  • 身份、权限、密钥和审计完整性异常；
  • DR 复制、备份和恢复校验失败。

不直接呼叫值班的指标进入趋势/容量计划，避免告警疲劳。

8. 事件管理

8.1 分级

级别 示例 目标
SEV0 交易错误扩散、重大数据/密钥泄露、核心状态不可证明 立即全员响应和管理层/合规介入
SEV1 Tier 0 大范围不可用、外部状态大量未知、关键数据截止失败 5 分钟确认、15 分钟建立指挥
SEV2 单领域显著降级、有替代路径、错误预算快速燃烧 15 分钟确认
SEV3 局部问题、无即时业务影响 工作时段处理

正式时限由组织排班、合规和业务等级确认。

8.2 角色

  • Incident Commander：决策、优先级和切换；
  • Operations Lead：技术恢复；
  • Business Lead：交易/产品影响和业务降级；
  • Communications Lead：状态更新和外部沟通；
  • Security/Compliance：数据、监管和证据；
  • Scribe：时间线、决定、动作和证据。

8.3 流程

检测 → 宣告/分级 → 限制影响 → 恢复服务 → 核对业务状态 → 沟通 → 根因与复盘 → 改进关闭

恢复 HTTP 服务不等于事件结束；订单、成交、持仓、资金、风险和数据缺口全部核对后才能关闭。

9. 运行手册与自动化

运行手册至少包含触发条件、前置检查、风险、权限、步骤、预期输出、停止条件、回退和验证。高风险步骤转换为类型化运维 Action：

  • 切换行情源；
  • 暂停/恢复账户或执行单元；
  • 查询外部未知订单；
  • 重放指定事件区间；
  • 扩容/限流；
  • 切换只读/降级；
  • 恢复备份或执行 DR。

动作需要幂等、范围预览、Maker-checker、审计和自动超时，取代长期依赖 screen、手工 crontab、共享 SSH 或 kill -9。

10. 容量与性能管理

  • 为用户、服务、Topic、数据库、搜索、图、向量和模型建立容量模型；
  • 按市场开盘、收盘、报告截止、批处理和回放模拟峰值；
  • Replay 环境运行 1×、2×、5× 负载和突发；
  • 观察延迟曲线、积压恢复时间、热分区、GC/IO、降级和成本；
  • Tier 0 保留可验证冗余，不能把自动扩容当作即时容量；
  • 容量阈值提前触发采购/扩容，避免只在 90% 使用率后处理；
  • 每次大客户、市场、账户或数据源接入均复核容量。

11. 发布可靠性

  • 发布事件进入所有相关仪表板；
  • 金丝雀按流量、账户、策略或只读影子划分，不能只按随机 Pod；
  • 自动回滚同时观察技术 SLI 和业务不变量；
  • 数据库、本体、策略和事件变化使用前向兼容；
  • 低时延交易发布在批准窗口，并有预热、连接和序号检查；
  • 发布后观察窗未结束前不宣布完成；
  • 错误预算不足、DR 不健康或审计中断时阻止非必要发布。

12. SRE 验收

  • 任意失败动作能从 action_id 定位 API、策略、工作流、事件和外部回执；
  • 任意异常指标能定位负责人、版本、最近变更和运行手册；
  • 仪表板显示业务时间和数据新鲜度，不仅显示采集时间；
  • 告警注入演练能在目标时间被接收、分级和处理；
  • 故障恢复后能自动生成待核对对象集；
  • 采样不丢失 Tier 0 错误、审计和安全证据；
  • SLO 月报能解释预算消耗来源并驱动发布决策。
