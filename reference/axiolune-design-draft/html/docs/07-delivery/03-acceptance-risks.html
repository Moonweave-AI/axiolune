验收体系与风险登记

1. 验收方法

验收采用“需求—控制—证据—责任”模型：

元素 说明
Requirement 用户旅程、业务不变量、法规/安全或非功能要求
Measure 可重复计算的 SLI、质量规则、测试或核对
Threshold 通过/阻断阈值及观察窗口
Evidence ValidationRun、Trace、报告、回执、签名和审计
Owner 提供证据的人与接受剩余风险的业务责任人

本文阈值分为“硬门”和“规划基线”。柜台时延、市场容量、法规留存等未获得真实输入前，不能伪造精确承诺；必须在阶段 0 固化并纳入 Release Gate。

2. 一级验收门

2.1 业务与范围

编号 验收项 通过标准
B-01 需求追踪 范围内每个关键旅程关联对象、动作、数据、测试和 Owner
B-02 语义确认 主键、时间、单位、枚举、null/zero 和指标口径全部批准或明确阻断
B-03 角色 UAT 每个核心角色完成正常、异常、降级和恢复旅程
B-04 一致结果 旧新差异全部分类；高风险/高金额未解释差异为 0
B-05 操作闭环 提交、审批、执行、回执、失败、补偿和核对均可追踪
B-06 非目标 延后能力和手工控制有责任人、时限和风险接受

2.2 本体与契约

编号 验收项 通过标准
O-01 类型完整 关键对象/链接/函数/动作/策略有稳定 API 名、Owner、版本
O-02 身份 规范 ID 唯一；19 位 ID 端到端按字符串；冲突进入隔离
O-03 兼容 未批准破坏性本体/API/Event/Data 变化为 0
O-04 影响 变更可列出数据、SDK、应用、策略、报告和消费者
O-05 分支/场景 变更可在隔离分支与 Scenario 运行且无生产副作用
O-06 退役 Deprecated 有替代、迁移、截止、消费者和 Owner

2.3 数据与算法

编号 验收项 通过标准
D-01 传输完整 文件/表/事件行数、哈希、序号和控制总数通过
D-02 质量 关键数据产品在 SLA 内；阻断规则失败不进入 Published
D-03 点时 财报、成分、分类、公司行动、股票池无未来信息泄漏
D-04 可复现 同快照/代码/参数/环境结果在批准容差内一致
D-05 核对 订单/成交/持仓/资金/净值截止点覆盖 100%，未解释差异为 0
D-06 精度 金额、价格、数量、比例按 ValueType，不经非批准浮点转换
D-07 证据 任意指标可追溯输入、快照、逻辑/模型版本和运行

2.4 安全与合规

编号 验收项 通过标准
S-01 身份 人员 MFA；服务短期身份；共享生产账号为 0
S-02 秘密 仓库/镜像/文档/日志 Secret Scan 无未豁免高危；已暴露值轮换
S-03 权限 对象/属性/链接/动作/导出/Agent 负向矩阵 100% 通过
S-04 职责分离 L3/L4 Maker 不能自批；审批绑定摘要/版本/时限
S-05 审计 生产动作、策略、审批和外部回执覆盖 100%，完整性校验通过
S-06 数据生命周期 分类、目的、保留、删除、外发和法定冻结有执行证据
S-07 安全测试 威胁模型、SAST/DAST/SCA、渗透和关键修复关闭
S-08 AI 严重越权检索/工具副作用为 0；高风险仅 proposal

2.5 可靠性与性能

编号 验收项 通过标准
R-01 SLO 观察期内达到批准 SLO，错误预算未超支
R-02 容量 1×/2×/5× 目标负载完成，背压/恢复和成本在预算内
R-03 幂等 API/事件/工作流重复、乱序、超时不产生重复副作用
R-04 外部未知 柜台未知状态可检测、查询、暂停和人工处置
R-05 故障 节点、网络、数据库、消息、来源故障演练达到预期降级
R-06 观测 action/order/event/trace 可关联；告警到人并有运行手册
R-07 恢复 备份隔离恢复和业务级 DR 达到实测 RPO/RTO
R-08 回退 金丝雀停止和按切换单元回退演练通过

2.6 用户体验与运营

编号 验收项 通过标准
U-01 状态完整 Loading/empty/error/denied/stale/degraded/partial 明确
U-02 实时 显示连接、来源、数据时间、延迟和恢复状态
U-03 高密度操作 目标数据量下虚拟表格、过滤、导出满足性能
U-04 可访问 键盘、对比度、非颜色状态、辅助技术达到批准标准
U-05 权限体验 拒绝原因和申请路径明确，不以空白隐藏
U-06 运维 关键任务无需共享 SSH、静态密码或手工进程管理
U-07 支持 Owner、值班、SLO、仪表板、告警、运行手册完整

3. 分阶段签署

阶段 必需签署
基线/范围 Sponsor、Domain Owner、Architecture、Security/Compliance
本体/数据发布 Domain Owner、Ontology、Data Owner/Steward
研究/模型 Research Owner、独立验证、Model Risk（按等级）
交易影子 Trading、Risk、SRE、QA、外部接口 Owner
生产动作 Business、Risk/Compliance、Security、SRE、Release
DR/退役 Business Continuity、Data Owner、Security、SRE、Sponsor

签署接受的是明确版本、范围、证据和剩余风险，不是泛泛“同意上线”。

4. 质量豁免

豁免必须包含：

  • 未满足的验收项和根因；
  • 影响对象、用户、金额、数据和环境；
  • 风险等级与最坏情景；
  • 临时控制和可观测指标；
  • Owner、Checker、到期日和修复里程碑；
  • 自动到期后的系统行为；
  • 禁止扩展的范围。

Tier 0 正确性、未授权动作、审计不可写、未知外部状态无法处置、无回退/恢复等不得以普通进度理由豁免。

5. 风险评分

使用概率 P(1–5) × 影响 I(1–5)：

  • 1–4：低，团队管理；
  • 5–9：中，月度跟踪；
  • 10–15：高，Steering 可见和明确缓解；
  • 16–25：极高，原则上阻止相应范围启动/上线。

金融风险还需记录暴露金额、监管/客户影响、可检测性和恢复时间；分数不能替代专业判断。

7. 风险处置状态

每项风险记录：

  • identified / analyzing / mitigating / accepted / transferred / closed；
  • 固有风险、控制后剩余风险；
  • 控制证据和最后验证时间；
  • 触发阈值、应急预案和决策人；
  • 到期/复审日；
  • 关联 Requirement、SystemComponent、DataAsset、ActionType、Incident。

风险关闭需要验证控制有效，不以“任务已创建”关闭。

8. Go/No-Go 清单

上线会议只回答证据化问题：

  1. 本次精确版本和切换单元是什么？
  2. 仍有哪些未通过项和已批准豁免？
  3. 新旧数据、规则和状态差异是什么？
  4. 谁能发起/批准/执行，权限是否刚复核？
  5. 峰值、故障、未知状态、备份和 DR 是否实测？
  6. 停止阈值、写入围栏、回退和核对由谁执行？
  7. 外部供应商、业务、风控、安全和支持是否就绪？
  8. 当前错误预算、复制、审计和关键依赖是否健康？

任一 Tier 0 硬门缺少证据即 No-Go。

9. 上线后成功标准

观察窗口应覆盖真实业务周期。成功不是“没有告警”，而是：

  • 所有纳入流量均由预期版本和路由处理；
  • 订单、成交、持仓、资金、净值和报告核对无未解释差异；
  • 用户任务成功率和耗时达到目标；
  • SLO/错误预算、数据新鲜度和质量稳定；
  • 权限拒绝、导出、审计和 Agent 行为符合基线；
  • 人工修复、临时权限和旧路径使用持续下降；
  • 事故/差异有关闭证据；
  • 观察期后可安全关闭旧写入、双跑和临时控制。

10. 最终平台验收

平台级完成需同时证明：

  • 多领域共享本体不是单应用特例；
  • 至少一个数据—决策—动作闭环在生产可审计运行；
  • 至少一次本体/契约兼容演进和消费者迁移完成；
  • 至少一次服务恢复和业务级 DR 达标；
  • 至少一条遗留权威路径被安全退役；
  • 用户、数据、可靠性、安全和成本指标持续两个或以上业务周期稳定；
  • 治理由常设 Owner/机制承担，不依赖项目临时团队。
