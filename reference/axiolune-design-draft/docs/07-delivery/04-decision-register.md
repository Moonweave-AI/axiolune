# 架构决策登记册

## 1. 已建议的基线决策

以下是设计基线，不是未经验证的采购单。每项在立项时形成独立 ADR，记录基准测试、许可证、运维 owner 和复核日期。

| ADR | 决策 | 主要理由 | 被否决的默认做法 | 重新评估触发器 |
| --- | --- | --- | --- | --- |
| ADR-001 | 本体是跨数据、逻辑、动作、安全的运行时契约 | 支撑统一对象、强类型动作、权限传播与代码生成 | 把 RDF/图数据库或数据字典称为完整本体 | 本体 API 无法满足关键延迟或一致性 |
| ADR-002 | PostgreSQL 保存事务、控制、账本和本体定义真源 | ACID、约束、审计、生态成熟 | 用图/搜索/缓存保存最终订单或余额 | 单库/分片实测无法满足容量与地域写需求 |
| ADR-003 | Kafka 传播事实，Outbox 连接事务 | 可重放、解耦、避免 DB/消息双写窗口 | 把 Redis Pub/Sub 当可靠业务总线 | 已有等价平台提供经验证的顺序、回放与治理 |
| ADR-004 | REST/OpenAPI 承担动作与外部契约；GraphQL 仅受控读取聚合 | 写入语义、幂等、审计和成本更明确 | 所有读写统一到 GraphQL | 受控领域查询证明可简化且授权/成本可审计 |
| ADR-005 | gRPC/Protobuf 用于内部同步 RPC | 强类型、低开销、跨语言 | 自定义二进制协议 | 低频边界用 HTTP/JSON 更易运维 |
| ADR-006 | Temporal 管业务长流程，Airflow 管批数据，Flink 管事件时间流 | 三类状态、恢复和人员协作语义不同 | 用一个调度器包办全部 | 组织已有平台经故障/审批用例证明等价 |
| ADR-007 | Iceberg v2 + Parquet 是湖仓开放格式基线 | 快照、演进、重放、引擎互通 | 把专有仓库表当唯一历史真源 | 既有 Delta/Hudi 生态的迁移成本显著更低 |
| ADR-008 | ClickHouse 是行情/分析投影，不是账本 | 高吞吐列式分析 | 在 PostgreSQL 上承担所有 Tick 聚合 | 工作负载规模不足以证明独立 OLAP 必要 |
| ADR-009 | OpenSearch 做全文/混合检索；pgvector 起步 | 降低首期组件数，复用过滤与权限 | 首日同时部署多套向量库 | 召回、规模、过滤和 P99 基准触发 Milvus |
| ADR-010 | 图事实留在 PostgreSQL/事件；Neo4j 仅为可重建投影 | 避免图数据库锁定身份与事务 | 图数据库作为本体唯一真源 | 多跳/GDS 基准与商业 HA 预算均满足 |
| ADR-011 | OpenMetadata + OpenLineage 为首期目录与血缘 | 一体化目录、域、质量、运行血缘 | 两套主目录并行 | 超大组织对元数据图/流式变更形成明确需求时评估 DataHub |
| ADR-012 | 单一 React 平台壳 + 领域包 | 统一身份、导航、Token、对象组件和发布 | 团队规模不足时先做微前端 | 多个自治团队确需独立发布和故障隔离 |
| ADR-013 | Java 负责核心域，Python 负责研究/AI，Rust/C++ 只进入实证低时延路径 | 控制语言数量并匹配负载 | 每个服务任意选语言 | 压测或厂商 SDK 明确要求 |
| ADR-014 | 企业 IdP + OPA + OpenFGA/SpiceDB + 数据层纵深策略 | 组合身份、属性、关系、用途和对象权限 | 只靠菜单/RBAC | 既有 IAM 能完整表达并通过负例测试 |
| ADR-015 | Agent 只调用类型化 Function/Action，权限为用户与 Agent 白名单交集 | 防止自然语言绕过策略和审批 | LLM 直连数据库/交易网关 | 无；这是安全不变量 |
| ADR-016 | 多模态原件保存在 S3 兼容对象存储，本体只保存引用 | 大文件生命周期、hash、转码与证据定位 | 在数据库 JSON/BLOB 内嵌媒体 | 特殊小对象的事务一致性有明确收益 |
| ADR-017 | 生产/仿真/测试是强制环境维度并物理/逻辑隔离 | 降低误操作与数据泄漏 | 只用页面颜色区分环境 | 无；只能提高隔离强度 |
| ADR-018 | 模块化核心起步，按一致性、负载与自治边界拆服务 | 避免“每页面一个微服务” | 首期大量分布式服务 | 团队、部署频率、故障域或容量形成实证 |

## 2. 决策所需证据

每个 ADR 至少包含：

- 问题、约束、假设和非目标；
- 候选、量化比较、三年 TCO 与许可证；
- 一致性、时延、容量、恢复、安全和人员能力；
- PoC 数据集、脚本、环境、结果和可重复步骤；
- 数据真源、同步、降级和退出方案；
- 责任人、批准人、决策日期、复核日期；
- 受影响的本体/API/事件/应用和迁移。

## 3. 禁止用“未来可能”引入组件

新增数据库、消息系统、语言、AI 框架或微前端必须由当前方案无法达到的量化指标触发。仅以“以后数据可能很大”“流行”“可扩展”不能通过架构门。
