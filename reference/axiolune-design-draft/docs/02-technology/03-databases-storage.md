# 数据库、搜索、图、向量与媒体存储

## 1. 多模型存储原则

平台不寻求“一库通吃”，而是为每个负载指定真源、投影和重建路径：

| 负载 | 真源 | 在线投影 | 重建来源 |
| --- | --- | --- | --- |
| 订单/动作/审批 | PostgreSQL + 追加事件 | PostgreSQL/缓存 | 事务日志、外部回执 |
| 逐笔/行情/分析 | Iceberg/Kafka | ClickHouse | 原始事件 |
| 本体定义 | PostgreSQL + Git 发布清单 | 本体缓存/SDK | 版本化定义 |
| 对象搜索 | 领域真源/湖仓 | OpenSearch | 对象变更事件 |
| 复杂关系 | 本体链接/领域真源 | 图投影 | 对象与链接事件 |
| 文档与媒体 | S3 原件 | 预览/全文/向量 | 不可变原件 |
| 向量 | 文档/对象/模型版本 | pgvector/OpenSearch/Milvus | 分块与嵌入清单 |

## 2. PostgreSQL

适用：

- 本体元数据、Schema、动作与策略版本；
- 用户配置、保存视图、任务、审批和评论；
- 产品、账户、组合、研究注册等事务；
- OMS/RMS 非超低延迟写模型；
- Outbox/Inbox 和审计索引。

设计要求：

- 每域独立 Schema/数据库所有权；
- 主键使用平台稳定 ID，业务自然键另建唯一约束；
- 关键表带版本和双时间；
- Decimal、时区、枚举和值对象严格映射；
- 高可用、连接池、只读副本、PITR；
- RLS/列权限作为纵深防御，不代替服务层策略；
- 大历史和分析数据及时归档到湖仓/ClickHouse。

何时评估分布式 SQL：单实例垂直与合理分片已不能满足写入/容量，且确有跨地域同步写；先以实际压测证明，不以“未来可能很大”为理由。

## 3. Kafka

Topic 按领域、事件类型和环境设计，键选择保证所需局部顺序。关键要求：

- 生产、仿真、回放彻底隔离；
- Protobuf/Avro Schema Registry；
- 幂等生产者和合理确认级别；
- 订单/成交保留足够重放窗口并落湖；
- ACL、配额、敏感 Topic 加密和审计；
- 监控 consumer lag、乱序、重复、DLQ 和 Schema 兼容；
- 不用 Kafka 保留无限期唯一副本。

## 4. Iceberg 湖仓

用途：

- 原始行情、财务、新闻、交易和审计归档；
- 规范化 point-in-time 数据；
- 因子、特征、回测、模型和报表结果；
- 可复现快照与历史重算。

按交易日/事件日期与高基数字段组合分区，避免过细小文件。使用 compaction、manifest 优化、快照过期和删除策略。表 Schema 与数据契约联动。

## 5. ClickHouse

适用：

- Tick、逐笔、K 线与盘口统计；
- 算法执行、延迟、撤单/错单和 TCA；
- 风险时序、组合敞口和经营报表；
- 大规模因子结果的交互查询。

设计：

- 明确排序键、分区键和主键稀疏索引；
- 使用物化视图生成常用粒度；
- 避免高频小更新，采用事件追加和版本/替换语义；
- 资源组隔离实时监控与重分析；
- 常用查询有基准数据集和 P95 预算；
- 真源在 Kafka/Iceberg/领域库，可重建 ClickHouse。

## 6. OpenSearch

索引对象、文档片段、报告和可搜索指标。每条文档携带：

- canonical object ID；
- object/type/version；
- business/system time；
- source/evidence；
- ACL/属性标记/用途；
- embedding model/chunk version；
- index timestamp。

查询先构造权限过滤，再做关键词、语义和关系扩展。高敏字段不进入索引或使用专门受控索引。

## 7. 图存储

### 7.1 本体真源与图投影分离

对象/链接定义、权限、动作和版本存 PostgreSQL/Git；图数据库保存为遍历优化的对象/链接投影。这样可以替换 Neo4j/NebulaGraph 而不改变业务契约。

### 7.2 选择建议

- Neo4j Enterprise：工具、查询、算法和企业能力成熟，适合预算充足、复杂调查/路径分析；
- NebulaGraph：适合大规模分布式图和国产化/私有化评估；
- JanusGraph：全 OSS、后端可选，但部署和一致性运维更复杂；
- PostgreSQL 递归查询：关系量和路径深度有限的首期方案。

触发专用图数据库的证据：对象/链接规模、典型 hop、查询并发、P95、更新频率和算法需求。不能仅因项目叫“知识图谱”而引入。

## 8. 向量存储

首期：

- 文档量中小时使用 pgvector；
- 已有 OpenSearch 时使用其 k-NN/混合检索；
- 检索结果必须与 ACL 和结构化本体过滤相交。

当向量达到大规模、需要独立扩展、多向量/复杂索引或现有方案无法满足召回和延迟时，评估 Milvus。迁移依赖原始 chunk、嵌入版本和索引配置清单，而不是从旧索引导出未知状态。

## 9. 对象存储与媒体

选择顺序：

1. 现有云平台受支持的 S3/OSS/COS/OBS；
2. 私有云使用 Ceph RGW 或经许可/支持审查的 S3 实现；
3. MinIO 只有在当前许可、功能、支持和升级路线满足组织要求时采用。

关键能力：

- 服务端加密和 KMS；
- 对象版本、Object Lock/WORM；
- 生命周期和跨域复制；
- 预签名 URL 最小期限；
- 分片上传、校验和断点续传；
- 病毒/恶意内容扫描；
- 文件哈希、MIME、大小、媒体元数据和来源；
- 原件、预览、OCR/转写和派生文件分层；
- 下载、预览、导出与分享审计。

## 10. 缓存

Valkey 用于：

- 短期对象/权限决策缓存；
- Web 会话、限流和分布式锁的谨慎场景；
- 实时订阅路由；
- 可重建热数据。

缓存必须有版本键、TTL、失效事件和击穿保护。订单、持仓、审批和审计不能以缓存作为唯一真源；Redis Pub/Sub 不用于需要可靠重放的业务事件。
