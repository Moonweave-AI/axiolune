### 7.2 风险缓解策略

#### R-001: 参考系统理解偏差

**缓解措施**:
1. **源码级追踪**: 每个概念链接到源代码行号
   ```yaml
   Equity:
     definition: "权益类证券"
     references:
       - system: nautilus_trader
         file: "nautilus_trader/model/instruments.pyx"
         line: 245
         url: "https://github.com/nautechsystems/nautilus_trader/blob/v1.195.0/nautilus_trader/model/instruments.pyx#L245"
   ```

2. **双人审查**: 每个概念由本体工程师定义，金融专家审查

3. **生产验证优先**: nautilus_trader > Lean > qlib，禁用design-draft

4. **示例驱动**: 每个核心类型附带真实使用示例

**监控指标**:
- 金融专家审查通过率 > 95%
- 概念定义返工率 < 10%

#### R-002: ADR-012时间语义实施错误

**缓解措施**:
1. **自动化检查**: validate-m2.js强制检查三轴绑定
   ```javascript
   if (isTemporalType(mapping) && !hasThreeAxes(mapping.temporal)) {
     throw new Error(`${mapping.targetType}: missing temporal axes`);
   }
   ```

2. **绑定模板**: 提供标准数据绑定模板
   ```yaml
   # templates/temporal-binding.yaml
   temporal:
     patternRef: "ax-pattern:BiTemporalSnapshot"
     validTime:
       from: {bindingType: directField, source: {dataset: "src", field: "business_time"}}
     knowledgeTime:
       from: {bindingType: directField, source: {dataset: "src", field: "received_at"}}
     availabilityTime:
       from: {bindingType: runtimeContext, contextField: "assertionTime"}
   ```

3. **端到端测试**: 每个数据绑定有集成测试验证三轴

4. **培训**: 团队成员必须通过ADR-012培训

**监控指标**:
- validate-m2.js temporal检查通过率 100%
- 时间查询bug率 < 1%

#### R-003: FIBO对齐不当

**缓解措施**:
1. **对齐工作流**:
   - Step 1: 本体工程师提议对齐
   - Step 2: FIBO专家审查
   - Step 3: 金融专家最终批准

2. **对齐文档化**: 每个对齐有rationale和verifiedBy

3. **分级对齐**: 
   - 核心20个 → exactMatch (强制)
   - 重要30个 → closeMatch (推荐)
   - 其余 → relatedMatch (可选)

4. **FIBO版本固定**: 使用FIBO 2024-Q3，记录vocabularyVersion

**监控指标**:
- 核心20个概念100% exactMatch
- 对齐审查通过率 > 90%

#### R-004: 中国市场特性遗漏

**缓解措施**:
1. **专项审查清单**:
   - [ ] T+1交易制度建模
   - [ ] 涨跌停板机制（10%, 5%, 20%）
   - [ ] 结算价vs收盘价
   - [ ] A股/B股/科创板/创业板差异
   - [ ] 债券回购订单类型
   - [ ] 交易单位（100股起）

2. **参考rqalpha**: 使用rqalpha作为中国市场权威参考

3. **中国金融专家审查**: 邀请熟悉A股的金融专家审查

4. **真实场景测试**: 使用真实A股数据测试T+1逻辑

**监控指标**:
- 中国市场清单100%覆盖
- 中国金融专家审查Approved

#### R-005: 模块循环依赖

**缓解措施**:
1. **严格分层**: 8层架构，只能向下依赖

2. **依赖图可视化**: 自动生成依赖图并审查
   ```bash
   node scripts/visualize-deps.js > docs/dependency-graph.svg
   ```

3. **validate-m2.js循环检测**: 自动检测并阻止循环依赖

4. **早期识别**: Week 1即建立依赖规则，每周检查

**监控指标**:
- 循环依赖数量 = 0
- 跨层依赖数量 = 0

#### R-006: 性能不达标

**缓解措施**:
1. **性能基准**: Week 4建立PIT查询基准测试

2. **索引优化**: 
   - logicalKey字段自动建立索引
   - 时间轴字段建立复合索引

3. **查询优化**:
   - 过滤条件前置
   - 避免笛卡尔积joins
   - 使用物化视图

4. **性能监控**: 每周运行性能测试套件

**监控指标**:
- PIT查询1000条 < 100ms
- 订单状态转换 < 10ms
- 内存占用 < 2GB (100万实体)

#### R-009: M3元本体变更影响

**缓解措施**:
1. **版本固定**: M2固定依赖M3 v0.5.0

2. **变更通知**: M3变更必须提前2周通知M2团队

3. **影响评估**: M3变更前评估对M2的影响

4. **迁移计划**: 如需升级M3，制定详细迁移计划

**监控指标**:
- M3版本锁定且不变更
- 如有变更，迁移计划完整

### 7.3 应急预案

#### 场景1: Week 5发现订单FSM设计缺陷

**症状**: 15状态FSM无法支持某些订单类型（如AlgoOrder）

**应急措施**:
1. **Day 1**: 召集紧急会议，评估影响范围
2. **Day 2-3**: 提出3个备选方案
   - 方案A: 扩展到20状态
   - 方案B: 引入子状态机
   - 方案C: 使用状态+子类型组合
3. **Day 4**: ADR决策，选定方案
4. **Day 5-7**: 实施变更，更新测试
5. **Day 8**: 审查通过，继续Week 6工作

**决策权**: 架构师 + 本体工程师

#### 场景2: Week 8发现性能严重不达标

**症状**: PIT查询1000条耗时500ms (目标<100ms)

**应急措施**:
1. **Day 1**: 性能剖析，识别瓶颈
2. **Day 2**: 制定优化方案
   - 数据库索引优化
   - 查询语句优化
   - 引入缓存层
3. **Day 3-5**: 实施优化
4. **Day 6**: 性能测试验证
5. **如仍不达标**: 
   - 降级方案: 放宽至200ms
   - 长期方案: Week 11专项性能优化

**决策权**: 数据工程师 + 架构师

#### 场景3: 金融专家审查大量拒绝

**症状**: Week 3金融专家拒绝了30%的工具类定义

**应急措施**:
1. **Day 1**: 分析拒绝原因（理解偏差? 参考源不当?）
2. **Day 2**: 与金融专家深度对齐，澄清需求
3. **Day 3-5**: 返工修正
4. **Day 6**: 重新提交审查
5. **如时间不够**: 
   - Week 3交付基础8个工具类
   - Week 4补充18个子类

**决策权**: 金融专家 + 项目经理

#### 场景4: 团队核心成员离职

**症状**: Week 6本体工程师离职

**应急措施**:
1. **立即**: 知识转移（3天）
2. **Week 7**: 
   - 临时方案: 架构师兼任本体工程师
   - 或外部招聘/内部调动
3. **Week 8**: 新成员到位并熟悉
4. **如无法到位**: 
   - 缩减范围: 8模块→6模块 (strategy/risk延后)
   - 延长时间: 10周→12周

**决策权**: 项目经理 + 管理层
