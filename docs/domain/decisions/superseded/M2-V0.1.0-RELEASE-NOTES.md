## Key Design Decisions

### 1. Three-Axis Temporal Semantics (ADR-012)

All time-varying facts carry three temporal axes:
- **validTime**: Business effective time (market close, trade timestamp)
- **knowledgeTime**: Assertion/revision time (when platform learned it)
- **availabilityTime**: Consumer access time (when platform made it queryable)

**Impact**: Prevents look-ahead bias in backtests; enables knowledge-time reproducibility; enforces fail-closed on missing availableFrom

**Validation**: 43 positive fixtures pass, 12 negative fixtures correctly rejected (temporal constraint violations)

### 2. ObjectType vs AssociationType Distinction

- **ObjectTypes**: Stable governance artifacts with business identity (FactorDefinition, StrategyDefinition, RiskLimit, OrderIntent) â€?no temporal fields
- **AssociationTypes**: Time-varying facts with context (Signal, PriceObservation, Execution, ExposureObservation, LimitBreach) â€?TemporalFact + ProvenancedFact patterns

**Impact**: Clear separation between stable definitions and time-varying observations; prevents "currentPrice" anti-pattern

### 3. Market Rules as Versioned Applicability

T+1, price limits, settlement cycles modeled as RuleApplicability associations (not geography-specific parallel ontologies)

**Impact**: Single EquitySecurity concept works for all markets; avoids "ChinaEquity" vs "USEquity" concept trees; handles regulatory changes over time

### 4. Signal as Intermediate Research Artifact

Research-to-Execution pipeline: Factor/Strategy â†?Signal â†?Order

**Impact**: Separates research output (Signal) from execution intent (OrderIntent); enables backtest reproducibility without coupling to live order system

### 5. External Status Mapping

ExternalOrderStatusMapping prevents broker/venue status codes from polluting canonical vocabulary

**Impact**: Canonical OrderLifecycleState remains clean; vendor-specific states mapped explicitly with versioning

## Known Limitations

### 1. SHACL Execution Not Automated
- **Status**: SHACL shapes generated and validated manually
- **Impact**: Cardinality constraint violations (5/10 portfolio negatives, 7/9 orders negatives) not yet mechanically enforced
- **Mitigation**: pySHACL runner setup planned as parallel infrastructure work
- **Timeline**: Post-v0.1.0

### 2. CQ Logical Constraints Not Automated
- **Status**: CQ-S4 future price constraint (portfolio-neg-006) not in automated validator
- **Impact**: Manual review required until SPARQL constraint probe implemented
- **Mitigation**: Will implement as SHACL-SPARQL constraint or dedicated CQ probe
- **Timeline**: Post-v0.1.0

### 3. State Machine Validator Not Implemented
- **Status**: CQ-OE6 (order lifecycle transitions) validated manually
- **Impact**: Invalid state transitions not mechanically rejected
- **Mitigation**: Dedicated state machine validator planned
- **Timeline**: Post-v0.1.0

### 4. M1 Materialization Untested
- **Status**: Semantic chains complete, but no actual M1 data ingestion tested
- **Impact**: None for M2 module completion; expected for production readiness
- **Mitigation**: Slice A/B prove semantic correctness; M1 materialization is separate gate (M2-PLAN Â§10)
- **Timeline**: Post-v0.1.0 (M1 production gate)

### 5. Real Order Submission Not in Scope
- **Status**: E5 models order semantics only; real external submission is L3/runtime gate
- **Impact**: None â€?this is M2-PLAN design decision (Â§6.4)
- **Mitigation**: Semantic vocabulary and lifecycle complete; external write operations remain behind separate security gate
- **Timeline**: Post-M2 (runtime implementation)
